# MH4G 发掘装备专项研究与实施约束

本文件记录 MH4G 发掘装备的已确认结构、真实存档证据和后续实现约束。发掘装备是 MH4G 装备系统的核心功能，不能照搬 MH3G 的装备模型，也不能直接复用现有公开修改器的整条记录重建方式。

## 研究范围与证据

已对以下三份真实 MH4G 存档完成 Blowfish 解密和校验和验证：

- `user1`：校验和 `1098913`；
- `user1.BACK`：校验和 `965449`；
- `user2`：校验和 `888799`。

装备箱位于解密后角色数据的逻辑偏移 `0x173E`，共 1500 格，每格 28 字节。当前装备另有一份 7 × 28 字节副本，位于逻辑偏移 `0x40`；对应装备箱索引位于 `0x104`，顺序为武器、胴、腕、腰、腿、头、护石。索引允许达到 1499。

## 三大复杂装备类型

装备阶段固定围绕武器、防具、护石三类实现。三类都使用同一份 28 字节原始记录，但必须采用不同字段视图。

### 武器

必须覆盖：

- 普通武器和发掘武器的装备 ID、三个装饰品位及固定标志；
- 发掘攻击档、斩味/弹匣/弓档、属性或异常状态、升级档、武器专属值、发光、研磨、孔数和动态稀有度；
- 极限强化：`0x13` 的常见值为无 `00`、攻击 `40`、防御 `80`、生命/吸血 `C0`，同时允许任意原始字节值；
- 操虫棍：`0x01` 猎虫等级、`0x0F` 猎虫类型、`0x14–0x1B` 猎虫实例八项属性；
- 轻重弩限制解除/极限突破及枪管、消音器、盾牌等弩专用改造标志。

轻重弩必须特别区分两个概念：`0x13` 是通用的攻击/防御/生命极限强化，不是弩的限制解除。三份真实存档中的轻重弩在 `0x01` 出现 `00`、`20`、`28`，证明该字节是位组合；当前推测 `bit 5 (0x20)` 和 `bit 3 (0x08)` 分别表示限制解除与弩配件，但两者的准确名称尚需一组只切换单项设置的前后存档确认。在确认前按两个独立原始开关显示，不能错误合并或覆盖。

### 防具

必须覆盖：

- 普通防具和发掘防具的装备 ID、强化等级及颜色原始值；
- 三个装饰品位，每个都是 16 位值，`bit 15` 单独作为固定/内置标志，剩余 15 位作为装饰品 ID；
- 发掘防具的抗性档、防御档、升级档、发光、研磨、孔数、动态稀有度和研磨要求；
- 所有防具均允许修改上述字段，不通过外观 ID 限制“自定义技能/孔位”。

这里的自定义技能通过装饰品 ID 和固定标志表达，不应把它误做成护石式的“技能 ID + 技能点”字段。孔数和三个实际装饰品记录分别编辑，不强制两者相互匹配。

### 护石

护石没有必要再分普通与“发掘模式”；装备类型固定为 6，不同护石等级由装备 ID 表示。必须覆盖：

- `0x01`：孔数；
- `0x02–0x03`：护石 ID/等级；
- `0x06–0x0B`：三个装饰品 16 位记录；
- `0x0C–0x0D`：技能 1 ID；
- `0x0E–0x0F`：技能 1 点数，按有符号 16 位解释；
- `0x10–0x11`：技能 2 ID；
- `0x12–0x13`：技能 2 点数，按有符号 16 位解释；
- `0x14–0x1B`：原始保留字节。

护石技能 ID、技能点、孔数和装饰品组合全部允许自由编辑，不做正常挖掘产出范围校验。真实样本中已经存在技能 ID 555、技能点 30 等自定义值，必须正常显示和写回。

主要参考项目：

- `Rokumaehn/mh4edit`：MIT，提供 MH4U 装备字段、枚举和部分发掘判定参考；
- `mikemow/MHsavEditor`：提供 MH4G 偏移和通用 28 字节视图参考，但没有明确许可证，只研究不复制；
- `kiocat/mh4editor`：MIT，提供按武器类型和防具部位划分的显式发掘外观 ID 表；其记录解析和写回实现不可靠，不能直接采用；
- MH4G Dex Build 7：提供名称、普通武器/防具属性和图片引用，但数据库中没有完整的发掘标记与参数枚举。

## MH4G Save Editor 0.24 界面对应关系

用户提供的实际运行截图显示，该 Java 修改器把装备箱当作统一的 28 字节十六进制表格，没有按装备类型切换专用字段。截图底部打开的是本研究使用的同一份 `user2`，界面位置也包含加密文件的 8 字节头：例如第 7 格显示 `0x17EE`，等于逻辑装备箱 `0x173E + 6 × 28` 再加文件头 `8`。

界面列与记录偏移的对应关系如下：

| Java 界面列 | 偏移 | 长度 |
| --- | ---: | ---: |
| 种类 | `0x00` | 1 |
| 等级/孔数 | `0x01` | 1 |
| 装备 ID | `0x02` | 2 |
| 属性值 | `0x04` | 1 |
| 属性类型 | `0x05` | 1 |
| 装饰珠 1～3 | `0x06–0x0B` | 3 × 2 |
| 锋利/技1 | `0x0C` | 1 |
| 附加能力 | `0x0D` | 1 |
| 技1值 | `0x0E` | 1 |
| 虫种类 | `0x0F` | 1 |
| 研磨/技2 | `0x10` | 1 |
| 稀有度 | `0x11` | 1 |
| 其它/技2值 | `0x12` | 1 |
| 极限强化/技2值 | `0x13` | 1 |
| 未知 × 4 | `0x14–0x1B` | 4 × 2 |

这些标题只是按字节位置复用，并不代表所有类型中的真实含义。例如：

- `虫种类` 只在操虫棍中表示猎虫类型，在其他武器中是瓶、炮击、笛音色等专属值；
- 护石的两个技能 ID 和技能点实际各为 16 位，Java 表格只是把相邻低/高字节分散在通用列中；
- 最后 8 个“未知”字节在操虫棍中正是猎虫实例属性；
- `极限强化/技2值` 在武器中是 `0x13` 极限强化，在护石中只是技能 2 点数的高字节。

因此该修改器适合作为偏移和旧修改值的证据，不适合作为新 UI 的字段分组依据。新编辑器仍沿用 `mh3u-se` 外观，但必须针对武器、防具、护石分别解释同一批字节。Java 修改器允许直接输入十六进制值，这也解释了 `user2` 中成组存在的自由修改装备。

### Java 修改器代码参考表的价值

实际运行截图中的“代码参考”弹窗不是动态解析结果，而是读取程序随附的明文数据文件。仓库源码和发布 JAR 中均可找到对应资源，因而它们比 Java UI 本身更有研究价值：

| 文件 | 当前覆盖 | 可用于确认 | 限制 |
| --- | ---: | --- | --- |
| `EquiptType.json` | `0x01–0x14` 共 20 类 | 存档装备类型编号 | 仅名称表 |
| `EquiptList.json` | 14 类武器 | `(类型, ID)`、日文名、发掘外观颜色 | 不含防具/护石；含 `dummy`、空名称和补齐区间 |
| `EquiptDecoration.json` | `0x0001–0x0121` 共 289 条 | 装饰品 ID、名称和主要技能效果 | 只用于与 Dex 交叉核对 |
| `StoneSkill.json` | `0x01–0x90` 共 144 条 | 护石技能 ID | 不代表 16 位字段只允许这些值 |
| `InsectType.json` | `0x00–0x17` 共 24 条 | 猎虫类型、切断/打击和能力说明 | 不包含猎虫实例八项数值结构 |
| `EquiptNature.json` | `0x01–0x09` | 火、水、雷、龙、冰及四种异常属性 | 不含属性数值档 |

其中装饰品和护石技能的 ID 区间与当前 Dex 成品数据一致；猎虫 24 类则是补全 `0x0F` 名称与能力说明的重要交叉来源。`EquiptList.json` 中发掘武器带有明确的红、黄、绿、蓝、紫外观名，适合校验显式发掘 ID 集，但其大量空名称和 `dummy` 记录证明不能把连续 ID 区间直接认作有效装备。

这些数据只参与事实核对和测试报告。该参考仓库没有明确许可证，成品数据仍以 Dex 为主来源，不直接复制其代码或整份资源；发生冲突时保留冲突报告，并以真实存档字段行为决定结构解释。

`user2` 的 105 件已知发掘武器覆盖大剑、片手、锤、太刀、斩斧、铳枪、弓、双刀、操虫棍和盾斧。第 86～102 格系统化排列了操虫棍、属性和装饰品组合，是确认字段含义的重要样本。

进一步与宿主机上的 K73 武器存档包
`k73.com_mh4gweaponsave/20150815071132/000011d7/user2` 逐条比较后，已经确认用户的 `user2` 并非只是包含相似的修改装备：两份存档都恰好有 181 条非空装备记录，按完整 28 字节记录做多重集比较时 **181/181 全部完全相同**，仅装备箱格号和排列顺序不同。因此这 181 条记录可以作为旧修改器批量生成值的可靠枚举样本；但它们只能证明字段如何存储，不能证明这些组合是游戏正常产出的合法值。

K73 原始排列尤其适合按武器类型识别成组变量：相邻记录通常只改变属性类型、属性值、斩味、攻击档、升级档、武器专属值、发掘选项、稀有度或研磨要求中的一项。后续建立下拉枚举时应保留这份原始分组关系，并同时保留任意原始值输入能力。

`user2` 第 1301 格是明显经过修改的发掘操虫棍：

```text
13 63 9D 00 54 07 C6 00 C6 00 C6 00 21 14 03 1D 0E 09 04 40 FF FF FF FF FF FF FF FF
```

- `0x01=63`：猎虫等级 99，超出正常样本的 0～11；
- `0x14–0x1B`：8 项猎虫实例值全为 `FF`；
- 该记录同时存在于装备箱和当前装备副本中。

这些记录证明：编辑器必须接受字段存储宽度内的任意值，不能因为数值不在参考枚举中而拒绝打开、钳制、清零或自动“修复”。

## 28 字节记录的已确认结构

| 偏移 | 长度 | 通用或按类型解释 |
| ---: | ---: | --- |
| `0x00` | 1 | 装备类型：0～20 |
| `0x01` | 1 | 防具强化等级；护石孔数；操虫棍猎虫等级；轻重弩改造标志 |
| `0x02` | 2 | 小端装备 ID |
| `0x04` | 1 | 发掘武器属性值档；普通操虫棍等类型可能另有含义 |
| `0x05` | 1 | 属性或异常状态类型 |
| `0x06` | 2 | 装饰品 1；`bit 15` 为固定标志，ID 使用剩余位 |
| `0x08` | 2 | 装饰品 2，同上 |
| `0x0A` | 2 | 装饰品 3，同上 |
| `0x0C` | 1 | 近战斩味、弩弹匣、弓档；发掘防具抗性档 |
| `0x0D` | 1 | 武器攻击档；发掘防具防御档 |
| `0x0E` | 1 | 发掘升级档 |
| `0x0F` | 1 | 武器专属值：瓶、炮击、笛音色、弩、猎虫类型等 |
| `0x10` | 1 | 发掘选项位 |
| `0x11` | 1 | 发掘动态稀有度，样本中 `09` 显示为稀有度 10 |
| `0x12` | 1 | 研磨要求档 |
| `0x13` | 1 | 极限强化；常见参考值为 `00/40/80/C0`，允许其他字节值 |
| `0x14–0x1B` | 8 | 操虫棍猎虫实例属性；其他类型必须原样保留 |

`0x10` 当前确认的位定义：

- `bit 0`：未研磨/锈蚀；
- `bit 1`：发光；
- `bits 2–3`：孔数；
- `bits 4–7`：含义尚未确认。

修改上述三个字段时必须进行掩码更新，只改目标位，禁止从零重建整个字节。

操虫棍的 `0x14–0x1B` 结合真实样本，当前最可信的逐字节解释为：

```text
力量, 体力/耐力, 速度, 火, 水, 雷, 冰, 龙
```

正常实例示例：

```text
36 24 5A 00 00 00 00 00
09 00 2D 00 00 00 00 00
4B 0C 26 00 00 01 00 00
48 36 36 00 00 00 00 00
```

`FF FF FF FF FF FF FF FF` 是现存自由修改实例，必须支持读取、写入、复制和导入。

## 数据模型与自由编辑原则

每件装备保存两个层面：

1. **原始层**：完整 28 字节，作为无损回写的唯一基础；
2. **字段视图层**：按当前装备类型解释字段，并允许用户修改。

不建立装备掉落合法性状态，不区分“标准模式”和“作弊模式”。对已经开放高级自定义的发掘武器、防具和护石，装备 ID、技能数值、孔数、装饰品组合、发掘参数和猎虫属性是否能在正常游戏中生成，由用户自行决定；编辑器只负责正确表达和写回存档字段。普通武器的发掘随机参数专用控件默认只读，既有原始值继续无损保存。

参考枚举用于下拉选项和解释数值，但每个枚举字段都必须允许保留或输入原始数值。原始十六进制导入需要校验记录长度、目标格号和字段编码范围，不校验组合是否合法。

## 无损写回规则

1. 从原始 28 字节副本开始应用字段级补丁，不从空记录重新序列化现有装备。
2. 编辑一个字段只能改变该字段负责的字节或位；其他字节必须逐字节保持一致。
3. 对未知枚举值提供“原始值 `0xNN`”选项，并允许直接输入字段宽度内的其他值。
4. 不根据游戏掉落规则校验技能值、孔数、装饰品、装备 ID 与发掘参数的组合。
5. 不自动把 `FF`、`42` 等值钳制为常见极限强化值。
6. 装饰品只在用户编辑对应孔位时更新，并保留其高位标志语义。
7. 1500 格全部处理，包括 1400～1499 的零基索引范围。
8. 批量导出必须包含版本、格号、解析字段和完整 28 字节原始值；批量导入采用全量预检和事务式应用。

## 当前装备副本

当前装备副本不能在每次保存时无条件用装备箱记录覆盖：

- `user1` 和 `user2` 当前副本与对应箱内记录一致；
- `user1.BACK` 的胴和腕副本与箱内记录在装饰品字节上已有差异；
- 这种差异可能是旧修改器只修改当前装备造成的，属于需要保留的现存状态。

处理规则：

1. 装备箱记录和当前装备副本各自保留原始 28 字节；
2. 未编辑时两者都完全原样回写；
3. 原本相等时，可对两份记录应用同一个字段级补丁；
4. 原本不等时，UI 显示差异警告，由用户选择只改箱内、只改当前装备或同步；
5. 禁止整条覆盖导致当前装备副本中特有的装饰品丢失。

## 参考项目不能直接复用的部分

`mh4edit` 的主要限制：

- 只处理 1400 格，会漏掉用户存档最后 100 格中的真实装备；
- 保存时从零重建 `0x10`，会清除未知高四位；
- 不解析和写回操虫棍 `0x14–0x1B`；
- 部分枚举包含额外修改值，可作为自由编辑参考，但不能把它误写成字段含义本身；
- 会重建当前装备副本，不适合保留用户存档中已经存在的副本分歧。

`MHsavEditor` 只加载 480 个装备格，字段主要按通用十六进制值编辑，当前装备与装备箱也没有可靠同步策略。

`kiocat/mh4editor` 正确按 15 × 100 显示 1500 格，显式 ID 表有价值；但其 28 字节解析存在错位，写入会清零大量字段，只能采用数据表，不能采用读写逻辑。

高级自定义的界面规格、攻击与属性换算、正常/越界/原始值三层预设和斩味七色反向任务，统一按 [`relic-equipment-advanced-customization.md`](relic-equipment-advanced-customization.md) 实施。本文件继续作为字段结构和真实存档证据基线。
