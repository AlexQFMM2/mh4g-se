# MH4G 配装数据解包研究记录

本记录保存 SQLite 配装数据层的原生证据和生成边界。研究结论已经接入
`tools/build_sqlite_data.py` 与 `data/mh4g.sqlite`；仓库仍不提交 ROM、ARC、`code.bin`
或 Dex 原始导出。

当前 SQLite 生成器版本为 `1.1.1`，数据库 SHA-256 为
`953f93054a695d9cd72005e0c1a31216f2735703f05f79a2118b3e5b342b2fd8`。生成器与验证器会强制
核对全部 435 条发掘武器的红、黄、绿、蓝、紫中文后缀，防止游戏原生基础名称覆盖外观颜色。
manifest 同时记录逻辑源名、全部输入哈希、原生 manifest 与上述 `code.bin` 哈希；完整重建仍要求
连续两次生成得到相同数据库字节。

## 研究样本

- 游戏解包：`D:\MH\MH4G-HD\cci_unpacked`
- 解压后 `code.bin` SHA-256：
  `b3cf0ad1f9abca6cd007f5bb5d560b9302576f457bee9baaf2cdf12c0ce8156a`
- 下表中的游戏虚拟地址等于文件偏移加 `0x100000`。
- Dex Build 7 只用于名称和字段指纹交叉验证；数值、记录数和表边界以该
  `code.bin` 为权威。

对 8,313 个 ARC、87,383 个内部资源和 40 种资源类型的清单扫描表明，RomFS 中与
配装有关的内容是名称、说明、界面、模型和贴图。没有发现普通装备参数、装饰珠关系或
发动技能阈值的独立资源表；这些核心数据位于 `code.bin`。

## 已确认原生表

### 防具

防具记录固定为 40 字节，五张表连续排列：

| 部位 | 存档类型 | 文件偏移 | 游戏地址 | 记录数 |
|---|---:|---:|---:|---:|
| 头 | 5 | `0xE550D0` | `0xF550D0` | 987 |
| 胴 | 1 | `0xE5EB08` | `0xF5EB08` | 972 |
| 腕 | 2 | `0xE682E8` | `0xF682E8` | 956 |
| 腰 | 3 | `0xE71848` | `0xF71848` | 956 |
| 腿 | 4 | `0xE7ADA8` | `0xF7ADA8` | 964 |

已确认字段：

| 偏移 | 含义 |
|---:|---|
| `+0x04` | 适用/模型标志 |
| `+0x05` | 稀有度减 1 |
| `+0x06` | 特殊标志；`0x80` 为动态发掘防具，`0x40` 类别名称仍待确认 |
| `+0x07` | 基础防御 |
| `+0x08` | 4 字节价格相关值 |
| `+0x0C～0x10` | 火、水、雷、龙、冰耐性，均为有符号 8 位值 |
| `+0x11` | 孔数 |
| `+0x1E～0x27` | 最多五组 `uint8 skill_id + int8 points` |

原生 `0x80` 标记在每个部位恰好有 250 条，共 1,250 条动态发掘防具。当前 CSV
每部位只标记约 120 条，并且存在同名普通装备误匹配，所以 SQLite 重建时必须改用
原生标志，不能继承旧 CSV 的 `is_relic`。`0x40` 在每个部位恰好有 84 条，共 420 条，
说明它也是稳定类别而非随机位，但在命名确认前不把它等同于发掘装备。

### 装饰珠

- 文件偏移：`0xE291FA`
- 游戏地址：`0xF291FA`
- 记录大小：8 字节
- 记录数：290，包含 ID 0“无”

字段为 `uint16 item_save_id`、孔数、技能树 1、技能点 1、技能树 2、技能点 2和标志位。
技能点是有符号 8 位值。代码中的边界检查明确要求装饰珠 ID `< 0x122`。

当前 `decorations.csv` 的 326 行来自 325 条制作配方加 ID 0。同一装饰珠道具可能有
多条制作配方，但游戏只有 289 个非空可编码装饰珠 ID。现有 ID 290～325 会被游戏
查询函数判为无效，SQLite 必须以原生 290 条记录重建。

近战核心字段：`+0x08` 为无倍率基础攻击，`+0x0A` 为防御，
`+0x0B` 为有符号会心，`+0x0C/+0x0D` 和 `+0x0E/+0x0F` 为两组属性 ID 与有符号
属性值（存储值乘 10），`+0x10` 为孔数，`+0x13` 为稀有度减 1，`+0x16` 的
`0x80` 位为发掘标记。

| 类型 | 文件偏移 | 记录数 |
|---|---:|---:|
| 重弩 | `0xE4FB30` | 157 |
| 轻弩 | `0xE513B8` | 185 |

远程核心字段：`+0x04` 为稀有度减 1，`+0x0C` 为无倍率基础攻击，`+0x0E` 为防御，
`+0x10` 为孔数，`+0x11` 为有符号会心，`+0x1C` 的 `0x80` 位为发掘标记。
弹种、装填、反动、弓蓄力等专用尾部字段仍保留原始字节，后续按武器类型单独命名。

武器原生发掘位与现有 CSV 的武器发掘集合一致；防具发掘集合不一致。
十四类武器合计 435 条原生发掘记录。

## 技能名称与发动阈值

`core_common.arc` 的 `msg\skillName_jpn` 是 LMD 文本资源，共 291 个槽：

- 槽 0 为“无技能”。
- 槽 1～277 是可显示的发动技能。
- 槽 278～290 是 13 个 DUMMY。
- “胴系統倍加”不在普通发动技能名称槽内，由游戏作为特殊效果处理。

Dex 的 `DB_Skl.csv` 有 278 条有效关系：1 条胴系統倍加加上 277 条普通发动技能，
与原生名称槽数量闭合。它完整提供 `发动技能 ID → 技能树 ID → 阈值`，但目前尚未在
`code.bin` 中定位到可独立导出的等价连续表。搜索结果说明该关系不是简单的
`tree_id + threshold` 定长顺序结构，可能按技能树分组、拆成多张数组或由代码间接索引。

因此 SQLite 的技能阈值暂定使用 Dex 表，并同时保存以下溯源信息：Dex Build 7 数据版本、
原生 291 槽名称表的逻辑哈希、278 条关系数以及“胴系統倍加为特殊项”的校验。继续逆向
阈值表不会阻塞防具、珠子和基础配装计算，但在 SQLite 生成前仍要加入若干公开阈值的
人工断言，例如攻击、达人、匠、装填速度和负面技能。

## 可重复导出

`tools/research/export_native_equipment.py` 从已解压 `code.bin` 导出防具、装饰珠和武器
核心表，并生成每张表的偏移、记录长度、记录数和 SHA-256 manifest。默认只接受上述
已知文件哈希：

```bash
python3 tools/research/export_native_equipment.py \
  /path/to/decompressed-code.bin \
  /tmp/mh4g-native-equipment
```

输出目录必须位于仓库外。SQLite 生成器后续应消费该导出结果，而不是在构建过程中依赖
固定绝对路径或直接读取 ROM。

## SQLite 落地结果与保留问题

已完成：

1. 原生 290 条装饰珠 save ID 已作为权威表，不再按制作配方编号。
2. 五部位共 4,835 件防具、十四类共 2,849 件武器已进入 SQLite；防具发掘标记使用原生
   `0x80` 位，武器使用原生导出标记。
3. 装备技能、装饰珠技能、技能树、发动阈值、防御、五耐性、孔位及适用性均已结构化。
4. 发掘武器攻击档拆为真攻击、会心和防御，发掘防具耐性拆为五个整数，运行时代码不解析
   显示字符串。
5. manifest 已覆盖 `code.bin`、原生导出 manifest、CSV 和 Dex Build 7 输入哈希；验证器直接
   检查 SQLite 完整性、外键、表集合、固定记录数和发掘标记。

保留问题：

- `+0x06 & 0x40` 防具类别仍未命名，不擅自等同于发掘装备。
- 部分武器专用尾部字段仍只按原始字节保留，不影响当前基础配装计算。
- 发掘装备最大强化值证据不足，数据库保持 `NULL`，客户端和服务端均显示未知。
- 护石与发掘装备的完整生成合法性仍未找到独立原生规则表，因此采用可举报、可由管理员修正的
  社区三态标注；这不会降低协议、ID、记录长度和数组边界的结构安全校验。
