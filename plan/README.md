# MH4G Save Editor 开发计划

本项目沿用 `mh3u-se` 的 Qt 界面风格和主要交互，不重新设计整体 UI。底层存档结构、数据集和装备编辑逻辑按 MH4G 重新实现。

## 当前进度（2026-08-18）

SQLite、平台协议和修改器整合已完成，并进入 `main` 分支 Windows Action 构建验证；尚未创建
正式发布标签，也未部署生产：

- `data/mh4g.sqlite` 已由 CSV、Dex Build 7 与 `code.bin` 原生表确定性生成，最终 SHA-256 为
  `56914473f536b6ec6d13d58e44b8f7a855ed6d4ae0f90409859339574b8e1b69`。
- 七格配装使用 `MH_LOADOUT v1 / mh4g`，每件装备保存完整 28 字节实例，未知字节、固定珠位、
  护石 16 位点数和猎虫实例不会因导入导出丢失。
- MH3G 的配装器、配装大厅、个人信息和关于页已经原样移植交互，仅替换 MH4G 数据、协议和
  存档写入适配；没有另做一套 UI。
- 大厅支持装备 AND、发动技能 AND、社区合法性和是否包含发掘装备筛选；详情使用只读配装器，
  一键导入预检全部 1,500 格并事务式写入七条记录。
- 配装器武器和防具选择均支持基于原生 `is_relic` 的“只看发掘”筛选；选中发掘实例后入口明确
  显示“发掘武器高级编辑”或“发掘防具高级编辑”，继续保留字段宽度内的自由修改原则。
- 读取存档后可从独立装备箱弹窗选取具体实例。弹窗按原始页/格顺序展示并列出三颗装饰珠，
  支持按装备名、珠子名和位置搜索，选择后复制完整 28 字节，不与数据库模板混排。
- 三款修改器的复选框外观已统一；4G 使用白底可见边框、蓝色选中态和内置白色勾号资源。
- 合法性固定为合法、非法、不确定三态。发掘标记仅按原生 ID 派生，不由客户端或随机参数猜测。
- SQLite 校验、Qt 编译、真实存档回归、28 字节核心测试和离屏主窗口/配装器/账号/SSL 冒烟已通过。

本段描述的是已进入源码 `main` 构建验证、但尚未上线的状态。生产 MHED 当前仍只运行迁移版本 4 和已发布的 MH3G 客户端，
在用户明确要求上线前不得导入 MH4G 数据、执行迁移 00005 或更新线上镜像。

## 第一版（v0.1）实施边界

第一版优先交付可实际使用的基础修改器，不等待发掘装备全部反向完成：

1. 支持加密 `user1`、`user2`、`user3` 的打开、校验、另存为和重新加载。
2. 道具箱完整显示 1400 格，支持按名称/ID 搜索以及修改道具 ID、数量和清空格子。
3. 装备箱完整显示 1500 格，支持按名称/类型/ID 搜索以及修改装备类型、装备 ID、等级/孔数和三个 16 位装饰品记录。
4. 每件装备始终保留完整 28 字节；基础编辑只补丁对应字段，`0x04–0x05`、`0x0C–0x1B` 等尚未在第一版界面解释的字段不得改变。
5. 提供完整 28 字节十六进制查看和高级原始记录替换，方便现有修改装备无损迁移，但不提供发掘武器、防具、猎虫、弩改造或极限强化的专用控件。
6. 第一版不校验装备组合是否合法，也不自动修复或清除未知值。

发掘装备专项研究保留为后续版本任务，不再阻塞基础编辑器发布。

## SQLite、配装器与社区合法性（本地已完成）

第一版的“不校验合法性”继续作为 MH4G 修改器的产品边界。护石和发掘装备的
完整原生生成规则未能从游戏数据中直接提取，也不再将逆向完整生成器作为 SQLite、
配装器或在线广场的前置条件。下一阶段按以下顺序进行：

1. 将道具、十四类武器、防具、装饰珠、技能、护石及发掘参数迁移到只读 SQLite，建立 manifest、
   逻辑哈希、数据版本和可重复生成校验。
2. 建立七格本地配装器、技能与面板计算，并接入事务式一键加入装备箱。
3. 为平台增加 `game=mh4g` 服务端适配器、公开筛选、详情弹窗、发布、点赞和举报。

SQLite 开工前的解包表地址、字段、数据缺口和可重复导出方式见
[`native-data-research.md`](native-data-research.md)。当前已确认防具、武器和装饰珠
原生表；发动技能阈值仍使用 Dex 关系表并接受原生名称槽和公开阈值断言校验。

### MH4G 社区合法性决策

这是针对 MH4G 特殊情况做出的产品取舍，不是为了省略合法性开发：

- MH3G 和 MH4G 游戏本身没有一套可供修改器直接调用的非法装备判定；正常流程只是由
  生成器保证产物落在原生范围内。这与已存在较完整合法性规则可供复现的 GU 不同。
- MH4G 最关键的护石和发掘装备规则没有以独立数据表出现在解包资源中，大概率与生成
  逻辑一起编译进 `code.bin`；只根据公开范围或零散样本无法证明规则完整。
- 护石来源、任务等级、发掘品质和武器/防具类型之间可能存在组合约束。不完整的自动规则
  会把真实原生装备误报为非法，或把无法生成的组合误报为合法；这比明确显示“不确定”
  更容易误导用户。
- 因此使用可修正的社区标注与举报机制，同时保留严格的存档结构安全校验。这能如实表达
  当前证据的确定程度，也允许随着实机样本和社区证据积累持续纠正。

具体实施规则：

- 公开配装的合法性只使用三个状态：`legal`（合法）、`illegal`（非法）、
  `uncertain`（不确定）。
- 发布者上传 MH4G 配装时自行选择状态，默认为“不确定”。
- 广场显示该状态并支持按合法性筛选；状态只影响展示与筛选，不限制发布、查看、
  下载、使用配装器打开或一键导入装备箱。
- 举报增加“合法性标注错误”原因；管理员核实后可在后台直接改为合法、非法或不确定，
  并记录审计日志。
- 修改器和服务端仍必须校验记录长度、字段宽度、数组越界、未知 ID 和无法安全解析等
  结构错误；这些安全校验不属于上述社区合法性状态。
- 未来若逐步确认某些护石或发掘装备规则，可作为发布时的参考提示，不改变三态社区标注模型。

完整的 MH3G 成功经验与 MH4G 交接边界见
<https://github.com/AlexQFMM2/mh3g-saveEdit/blob/main/docs/MH3G_COMPLETION_RECORD.md>。

## 基本原则

- 使用真实 MH4G `user` 存档进行验证，保存前后都校验文件大小、加密头和校验和。
- 未确认含义的字节默认保持原值，不提供可能损坏存档的盲目编辑。
- 第三方修改器只用于研究格式和交叉验证，不直接复制无明确许可的代码。
- 每一阶段都先完成只读解析和原样回写测试，再开放编辑功能。

## 第一阶段：反向数据库

目标：从 `D:\MH\DEX\MH4G_Dex_v1.0Build7` 提取 MH4G 修改器需要的数据集。

工作内容：

1. 以 `D:\MH\DEX\mh3g-dex-dump` 为参考，制作 MH4G Dex 专用的运行时导出工具。
2. 处理 Dex 的字符串混淆、SQLite 数据库加密以及运行时初始化流程。
3. 导出并整理以下数据：
   - 道具 ID、名称和分类；
   - 武器 ID、名称、类型、稀有度和专用属性；
   - 防具 ID、名称、部位、稀有度和基础属性；
   - 装饰品、技能和技能树；
   - 武器斩味、属性、瓶、炮击、笛子音色、弩弹、弓箭类型等枚举；
   - 操虫棍和猎虫相关数据；
   - 可合法提取和使用的装备图标资源。
4. 将原始导出结果与程序使用的数据文件分开保存，建立可重复执行的转换流程。
5. 使用公开资料和真实存档中的 ID 交叉验证数据，避免混入 MH4U 或其他版本的编号。

验收条件：

- 导出过程可重复执行，不依赖手工复制表格内容。
- 道具、武器、防具、装饰品和技能的 ID 能与真实 MH4G 存档对应。
- 数据文件包含明确的来源、字段说明、记录数量和生成方式。

## 第二阶段：重构 UI 界面

目标：沿用 `mh3u-se` 的 Qt 界面设计，将界面与 MH3G 专用数据结构解耦，接入 MH4G 后端。

工作内容：

1. 沿用主窗口、菜单、标签页、搜索筛选、表格和编辑弹窗的布局与操作方式。
2. 将存档读写、数据集查询和 Qt 界面分层，避免 UI 直接依赖 MH3G 类型。
3. 建立 MH4G 存档模型和统一错误处理：
   - 识别 81,408 字节的 `user1`、`user2` 存档；
   - 解密、校验、编辑、重新计算校验和并加密；
   - 默认保留原文件，并支持另存为和备份提示。
4. 将装备箱界面容量由 MH3G 的 1000 格调整为 MH4G 的 1500 格。
5. 将单件装备原始记录由 16 字节调整为 28 字节，并保留只读原始字节查看功能。

验收条件：

- 三份现有测试存档均可打开并正确显示角色名称。
- 不做任何编辑时，保存后重新解密的数据区与原始数据一致。
- UI 外观和操作习惯与 `mh3u-se` 保持一致，底层不再依赖 MH3G 数据结构。

## 第三阶段：处理道具

目标：优先完成结构简单、风险较低的道具箱修改功能。

已确认结构：

- 道具箱逻辑偏移：`0x015E`；
- 容量：1400 格；
- 每格 4 字节：`uint16 ID + uint16 数量`。

工作内容：

1. 显示格子、道具名称、ID 和数量。
2. 支持名称与 ID 搜索、分类筛选和只显示非空格。
3. 支持单格新增、修改、清空以及合法数量校验。
4. 支持道具箱 CSV 表单导出和批量导入。
5. 导入前完整校验表单；出现错误时不修改任何存档数据。
6. 对三份真实存档进行修改、保存、重新加载和校验和测试。

验收条件：

- 1400 格全部可读取和写回。
- 非道具箱区域在编辑前后保持不变。
- 非法 ID、非法数量、重复格号和越界格号均会被拒绝。

## 第四阶段：处理装备

目标：安全支持 MH4G 的 1500 格装备箱和复杂装备定制数据。

发掘装备的真实存档证据、字段表、兼容旧修改器数据的规则和未解决项见 [`relic-equipment.md`](relic-equipment.md)；高级自定义控件、真实值/面板值换算、正常与越界预设、斩味七色方案以及分阶段验收见 [`relic-equipment-advanced-customization.md`](relic-equipment-advanced-customization.md)。两份专项约束都是本阶段实现和验收的组成部分。

已确认结构：

- 装备箱逻辑偏移：`0x173E`；
- 容量：1500 格，必须包含最后 100 格；
- 每件装备固定 28 字节；
- 三个装饰品位于字节 `6-11`，每个记录的最高位还包含固定标记；
- 字节含义会随防具、护石和不同武器类型变化。

### 4.1 通用装备模型

1. 建立保留全部 28 字节的原始记录模型。
2. 支持装备类型、ID、装饰品和原始字节的只读浏览。
3. 未识别类型只允许导出和查看，不允许危险写入。
4. 只校验记录长度、格号、字段存储宽度和装备类型等结构边界，不校验技能数值、孔位或属性组合是否符合游戏掉落规则。
5. 所有编辑从原始记录应用字段级补丁，禁止重建整条记录时清零未知字节。

### 4.2 防具与护石

1. 普通防具：装备 ID、强化等级、颜色和装饰品。
2. 发掘防具：防御、抗性、稀有度、发光、研磨状态和发掘类型。
3. 护石：护石类型、孔数、两组技能和有符号技能点、装饰品。
4. 发掘防具显式 ID 只用于名称标记和默认展开专用字段；所有防具均可手动编辑发掘参数，不因 ID 未命中参考表而限制保存。
5. 护石技能值、孔数及装饰品组合允许自由编辑，只受字段实际存储宽度限制。
6. 配装器防具候选支持“只看发掘防具”；选中显式发掘 ID 后，卡片直接显示发掘防具高级编辑
   入口，完整保留防御、五耐性、升级、孔位、动态稀有度、研磨、锈蚀和发光字段。

### 4.3 普通武器

1. 按武器类型显示装备 ID、强化等级、装饰品和极限强化。
2. 根据武器类型增加专用字段：
   - 斩斧、盾斧的瓶类型；
   - 铳枪炮击类型与等级；
   - 狩猎笛音色；
   - 轻弩、重弩的弹匣、特殊射击、限制解除/极限突破及枪管、消音器、盾牌等改造位；
   - 弓的蓄力与箭种；
   - 操虫棍的猎虫类型和等级。

### 4.4 发掘武器与操虫棍

1. 发掘武器按类型处理攻击、会心、防御、斩味、属性、异常状态和稀有度档位。
2. 处理研磨、发光、孔数、发掘等级及极限强化位标记。
3. 操虫棍额外处理字节 `20-27`：猎虫力量、体力、速度和火、水、雷、冰、龙属性。
4. 使用按装备类型划分的显式发掘 ID 集辅助标记发掘外观，不再通过名称颜色后缀猜测；轻弩 ID 29 标记为普通武器。
5. 发掘专用字段允许手动输入字段宽度内的任意值，包括 `FF`、`42`、猎虫等级 99 等现有改造值，不实现掉落合法性或组合合法性校验。
6. 普通武器 ID 携带的既有发掘参数必须显示提示并无损保留，但发掘随机参数专用控件默认只对 `is_relic=1` 的武器开放；普通武器不因基础编辑而改变这些字节。
7. 装备箱和新建/编辑弹窗均提供基于 `is_relic=1` 的“只看发掘武器”筛选，并与名称、ID、装备类型等筛选组合生效。
8. 配装器发掘武器卡片提供明确高级编辑入口，不另造编辑器；继续复用现有攻击、属性、斩味、
   专用参数、孔位、研磨、极限强化和猎虫实例控件。

### 4.5 当前装备副本

1. 分别保存逻辑偏移 `0x40` 的 7 条当前装备副本和装备箱原始记录。
2. 当前副本与箱内记录原本相等时，可对两者应用相同的字段级修改。
3. 两者原本存在差异时显示警告，由用户选择修改目标或主动同步。
4. 禁止保存时无条件用装备箱覆盖当前装备副本。

### 4.6 装备批量导入导出

1. 导出包含 1500 格、装备类型以及完整 28 字节的版本化 CSV 表单。
2. 导入时先解析到临时模型，完成长度、格号和字段编码等结构验证后一次性应用。
3. 表单中未列出的格子保持不变，禁止因部分错误产生半完成修改。
4. 导入前显示覆盖范围，并建议用户保留原始存档备份。

验收条件：

- 1500 个装备格均能正确读取和写回，包括第 1401～1500 格。
- 不支持的字段和保留字节不会因编辑其他字段而被清零。
- 各类装备使用独立、经过验证的字段定义和编辑面板。
- 修改后的存档通过解密校验、重新加载测试，并能由游戏实际读取。

## 阶段依赖

```text
反向数据库
    ↓
重构 UI 与 MH4G 存档核心
    ↓
道具箱编辑
    ↓
装备只读浏览与通用模型
    ↓
防具/护石 → 普通武器 → 发掘武器/操虫棍
    ↓
装备批量导入导出与实机验证
```
